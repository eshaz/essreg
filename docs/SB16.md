# The Sound Blaster 16 model

`tests/sb16.py` is a Creative Sound Blaster 16 at the port level: the DSP
(CT1741, firmware 4.05), the CT1745 mixer, the card's two DMA engines on a
model of the PC's DMA controllers (`tests/dma8237.py`), and its interrupt
line. It is the reference that the two Sound Blaster 16 fronts are tested
against, `esssb16.com` in DOS and `ES1869.VXD`'s front in a DOS box. This
page lists what the model does, how the fronts reproduce it on the ES1869,
and where each fact comes from.

The DSP's behavior follows Creative's own firmware, as the S95Sedan
CT1741_DSP disassembly of the 4.04 to 4.16 ROMs shows it. That disassembly
reassembles byte for byte, and its cold-boot RAM matches a dump of a real
card in DOSBox-X. The mixer follows Creative's Sound Blaster Series Hardware
Programming Guide, and the ADPCM decoders are DOSBox-X's. Where the sources
disagree, the firmware wins, and real hardware over emulators.

## The ports

The card answers at Audio_Base+4h to +Fh:
* **+4h, +5h**: the mixer's index and data. The index reads back as written.
* **+6h**: the reset. Only bit 0 matters, and a repeated write does nothing.
* **+Ah**: the read data, one byte at a time. A second read returns the same
  byte.
* **+Ch**: commands and their operands. A read gives bit 7, set while the
  input latch is full or the firmware is busy, and bits 6:0 set.
* **+Eh**: bit 7 set while a byte waits at +Ah, bits 6:0 set. The read
  acknowledges the 8-bit interrupt: the 8-bit engine's, F2h's and MIDI
  input's.
* **+Fh**: reads FFh and acknowledges the 16-bit interrupt.

The other ports of the range read FFh. The interrupt line is the OR of the
8-bit, 16-bit and MPU-401 interrupts, and the PIC sees its rising edge.

## Reset and boot

Writing 1 to +6h holds the firmware in reset: both engines stop, the busy
bit stays set, and the latches clear. Writing 0 starts the firmware, which
writes AAh about 50 us later. A cold boot sets the rate generator to 38h
(9958 Hz), the 8-bit block length of 48h to 07FFh, the speaker flag off,
both engines stopped and the 8-bit format to unsigned mono. It leaves the
test register of E4h, the CSP's ID and the mixer.

The high-speed commands (9xh) and the MIDI UART mode (34h-37h) set a
warm-boot signature, which a completed 8-bit single-cycle transfer clears. A
reset after them is a warm boot, which keeps the rate, the block length and
the speaker flag.

## Commands

Each command takes the operands the firmware reads after it, and each answer
goes out through the read latch a byte at a time: the firmware writes the
next byte once the program has read the last. A command written while an
answer waits is taken after the answer has been read. F8h is the exception:
its 00h overwrites an unread byte at once.
* **00h-0Fh**, the CSP's commands. Without a CSP, 03h, 08h and 0Fh answer
  FFh, 01h answers 00h and then FFh, 02h waits for the next byte and takes
  it as a command, 0Bh and 0Ch hang until a reset, and 04h, 05h and 0Eh
  write to nothing. 08h takes no operand.
* **10h-13h**, the direct DAC, one byte. **20h-23h**, the direct ADC, one
  byte back.
* **14h-17h**, the 8-bit and 2-bit ADPCM single-cycle transfers, with a
  length; **18h-1Fh**, their auto-initialized forms, with 48h's length.
* **24h-27h** and **28h-2Fh**, the 8-bit recordings, single-cycle and
  auto-initialized.
* **30h-33h**, MIDI input until the next byte the program writes, which the
  firmware drops; **34h-37h**, the MIDI UART mode until a reset;
  **38h-3Fh**, one MIDI byte out.
* **40h**, the time constant; **41h** and **42h**, the rate in Hz, high byte
  first. Both set the rate generator for the next start or continue.
* **48h**, the 8-bit block length, low byte first.
* **74h-77h**, the 4-bit and 2.6-bit ADPCM single-cycle transfers;
  **70h-7Fh** otherwise, their auto-initialized forms.
* **80h-8Fh**, silence for a length of sample periods, then the 8-bit
  interrupt.
* **90h-9Fh**, the high-speed 8-bit transfers, with 48h's length.
* **B0h-BFh**, the 16-bit transfers, and **C0h-CFh**, the 8-bit ones: bit 3
  records, bit 2 auto-initializes, bit 1 turns the FIFO on and bit 0 is
  ignored. Three operands follow: the mode, with bit 4 signed and bit 5
  stereo, and the length in samples less one, both channels counted. A Cxh
  transfer's length becomes 48h's too.
* **D0h** and **D4h**, pause and continue the 8-bit transfer; **D5h** and
  **D6h**, the 16-bit one. **D1h** and **D3h** set the speaker flag, which
  **D8h** answers (FFh or 00h), and change nothing in the sound. **D9h** and
  **DAh** end the 16-bit and 8-bit auto-initialize after the block that
  plays.
* **E0h**, the operand inverted. **E1h**, the version, 04h 05h. **E2h**, the
  DMA identification, which writes one byte through the 8-bit channel.
  **E3h**, the copyright, "COPYRIGHT (C) CREATIVE TECHNOLOGY LTD, 1992."
  with a 00h at the end. **E4h** and **E8h** write and read the test
  register. **E7h** answers nothing.
* **F0h**, the sine test. **F2h** and **F3h**, the 8-bit and 16-bit
  interrupts. **F4h**, the ROM's ID, 7Dh 1Bh. **F8h**, 00h. **F9h** and
  **FAh** read and write the firmware's RAM, and **FBh**, **FCh** and
  **FDh** read three of its status bytes.

The commands the table doesn't name do nothing and take no operand.

## Transfers

The DSP has two DMA engines. The 8-bit one runs Cxh and every older command,
on the 8-bit channel. The 16-bit one runs Bxh, on the 16-bit channel, or on
the 8-bit channel when mixer 81h gives no 16-bit one, two bytes a sample.
Each engine has its own format, length, count, auto-initialize flag and
interrupt, so both can run at once. One rate generator serves both, at v *
44100 / 248 Hz, a frame a period for stereo.

A transfer command starts its engine anew, cutting a block that runs without
its interrupt. The one exception is a single-cycle command of an engine that
runs auto-initialized: the firmware reads its mode byte and drops it, keeps
its length, and ends the auto-initialize with that one last block. At the
end of an auto-initialized block, the engine raises its interrupt and starts
the next block; if the last block's interrupt is still unacknowledged, it
waits for the acknowledge or for any byte the program writes to +Ch. A
single-cycle block's end raises the interrupt and stops the engine. D0h and
D5h stop the block ends of both engines until D4h or D6h. The older 8-bit
commands keep the format bits that the last Cxh, 10h, 20h, F0h or reset
left, and mixer 0Eh's stereo bit has no effect, because the CT1745 has no
0Eh.

An ADPCM block without a reference byte (74h, 76h, 16h) goes on from the
last block's reference and step, so that a stream of blocks plays as one, as
Creative's guide has a game send the first block with its reference byte and
the others without. A block ends once the codes of its last byte have
played. The ES1869's data sheet describes the same blocks for its
Compatibility mode (DS p.44), and the chip model plays them so.

## Rates

40h's time constant T gives v = 1000000 / (256 - T) * 248 / 44100, rounded
down, with T no higher than EBh. Two values are the firmware's own: 68h
gives 25h and 6Ch gives 26h, and before 4.13, C8h gives C8h, 35.6 kHz, an
error in the ROM's table. A5h gives 10847 Hz, D3h 22050 Hz and E9h 43389 Hz.

41h and 42h give v from the rate in Hz. Below 4864 Hz v is 1Ch, from 45312
Hz it is FFh, and in between the firmware multiplies by 23 in two bytes.
Before 4.13 it loses the carry between them, so some rates come out lower:
23000 Hz plays at 20094 Hz. `rate_to_v()` in `tests/sb16.py` computes it as
the firmware does.

## The mixer

The CT1745 has the registers below; the others read 00h.
* **00h**: the reset, which sets 04h-47h to their defaults and leaves 80h,
  81h and the index.
* **04h, 22h, 26h, 28h, 2Eh**: the Sound Blaster Pro's voice, master, MIDI,
  CD and line, views of the Sound Blaster 16's levels, a nibble a channel. A
  write sets each level to its nibble with 08h; a read gives the levels'
  high nibbles. **0Ah**: the mic's 3 bits. 0Ch and 0Eh aren't there.
* **30h-3Ah**: master, voice, MIDI, CD, line, left and right, and the mic, 5
  bits each (bits 7:3). Master, voice and MIDI reset to C0h, the others to
  00h.
* **3Bh**: the PC speaker, bits 7:6.
* **3Ch**: the output switches: line left and right (bits 4 and 3), CD left
  and right (2 and 1), the mic (0); 1Fh after a reset.
* **3Dh, 3Eh**: the input switches of the left and right recording: MIDI
  (bits 6 and 5), line (4 and 3), CD (2 and 1), the mic (0); 15h and 0Bh
  after a reset.
* **3Fh-43h**: the input and output gains (bits 7:6) and the mic's AGC (bit
  0). **44h-47h**: treble and bass, left and right (bits 7:4), 80h.
* **80h**: the IRQ, bit 0 for IRQ 2 or 9, bit 1 for 5, bit 2 for 7 and bit 3
  for 10, with bits 7:4 set, so F2h for IRQ 5.
* **81h**: the DMA channels, bits 0, 1 and 3 for channels 0, 1 and 3, bits
  5-7 for channels 5-7. A write picks the lowest of bits 5-7 as the 16-bit
  channel, or none.
* **82h**: the pending interrupts, bit 0 the 8-bit one, bit 1 the 16-bit one
  and bit 2 the MPU-401's, with the revision 2 in bits 7:4. Reading it
  acknowledges nothing.

## The fronts on the ES1869

The ES1869 answers a program as a Sound Blaster Pro, version 3.01, and plays
16-bit sound only in its own Extended mode, so both fronts answer the
program themselves and give the chip only what it needs to play. The DSP's
answers, its read latch, the version, the copyright, the tests, the rate
generator and the boot's settings come from the front, which never resets
the chip for a program's reset, because the reset would take the chip out of
Extended mode. Every PCM transfer plays or records on Audio 1 in Extended
mode, with the rate generator's rate turned into A1h and A2h as ES1869.DRV
computes them. The firmware's commands that Extended mode lacks, the direct
DAC and ADC, ADPCM, silence and MIDI, go to the chip in Compatibility mode.
[VXD_INTERNALS.md](VXD_INTERNALS.md#a-sound-blaster-16-for-dos-programs)
describes both fronts.

What a program can still tell apart:
* Audio 1's FIFO holds 256 bytes and takes the DMA ahead of the DAC, so a
  block's interrupt comes when its last byte is in the FIFO, up to 256 bytes
  before the DAC has played it.
* E2h writes no byte through the DMA, because a front has no way to.
* The chip takes one byte a DMA cycle on any channel, so a 16-bit transfer
  runs on Audio 1's 8-bit channel, two bytes a sample. The front carries the
  game's programming of its 16-bit channel over, and answers the count it
  reads from Audio 1's channel. Under EMM386, which doesn't trap the DMA
  controllers, `esssb16` reads the 16-bit channel back at each 16-bit
  command instead, so the game must program it first, and its count stands
  still.
* The master level has 6 bits on the chip and 5 on the CT1745, and the PC
  speaker 3 and 2, so a program that writes back the levels it read can move
  an odd chip level by a step.
* A program that uses the chip's Extended mode itself (C6h followed by a
  register command) gets the chip as it is until its next reset.

## The tests

`tests/sbgame.py` is a game's sound driver: the reset handshake, DSP writes
and reads that poll the status bits, the mixer, the DMA controller's
programming as Creative's guide gives it, and the interrupt handler. It runs
on a card, which is the model (`ModelCard`) or a front in front of the model
of the chip (`tests/esschip.py`, in `tests/sbfronts.py`).
`tests/sbscenes.py` holds what games do, as scripts that return what the
game saw. `tests/test_sb16conf.py` runs every scene on the model and on each
front, under QPIEMU, EMM386 and HDPMI32i and in a DOS box, and compares the
results, allowing only for the differences above. `tests/test_sb16front.py`
checks what the fronts send the chip ([TESTING.md](TESTING.md)).
